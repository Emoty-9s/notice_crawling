# 공통 증분 수집

초기 기준일은 **2026-11-06 KST**다. 게시일로 신규 공고를 차단하지 않는다. 목록에서 계산한 안정적인 `notice_id`에 해당하는 실제 Notice/history가 있어야 상세 요청을 생략할 수 있다. 인덱스에만 있고 history에 없는 ID는 반드시 수집한다.

기준일 전에 이미 수집한 ID(`first_seen_at`의 KST 날짜 기준)는 저장된 본문·분석·OCR을 재사용한다. 기준일 이후 처음 발견한 과거 게시 공고도 수집하며, 최근 게시·최초 발견일 중 최근 날짜가 7일 범위 안이면 제한적 변경 확인 대상이 된다. 기본 변경 확인은 기관별 최대 20건, 6시간 간격이며 목록 메타데이터 변경은 간격과 관계없이 확인한다. 최근 확인이 오래된 공고부터 순환한다.

## 페이지 탐색

기존 7개 기관의 최신순 정렬은 별도 검증되지 않았으므로 모두 기존 3페이지 탐색을 유지한다. 게시일 없는 목록이나 순서 역전이 있는 목록도 조기 종료하지 않는다. 신규 기관도 기본값은 동일하게 안전한 기존 탐색이다.

사이트별 검증이 완료된 경우에만 `sites.yaml`의 해당 기관에 다음 옵션을 명시한다.

```json
"incremental": {
  "latest_first_verified": true,
  "consecutive_known": 10,
  "max_pages": 100,
  "recent_refresh_limit": 20,
  "recent_refresh_hours": 6
}
```

검증된 정렬에서도 전체 페이지의 ID를 먼저 확인한다. 그 페이지에 신규 ID가 하나라도 있거나 최근 7일 범위를 지나지 않았으면 기수집 연속만으로 중단하지 않는다. 신규 공고가 여러 페이지에 있으면 기존 3페이지를 넘어 다음 관측된 페이지를 따라간다. 안전 페이지 상한에 도달하면 범위 미완료를 기록하고 성공 기준점은 갱신하지 않는다. 인위적으로 페이지 URL이나 POST 계약을 추측하지 않는다.

## 영속 상태·복구

- `data/crawl_state.json`: 기관별 자체 최초 기준점, `last_successful_crawl_at`, 수집한 ID·게시일·목록 지문·최근 상세 확인 시각.
- `data/crawl_diagnostics.json`: 기관별 확인 범위, 목록 페이지/HTTP 요청, 상세 요청/생략, 신규·최근 재확인, 정렬·조기 종료·fallback 상태.
- 신규 상세와 OCR 작업 명세를 Notice/history에 먼저 저장한 뒤 성공 기준점을 기록한다. OCR 이전 중단에도 다음 실행에서 ID와 미처리 이미지·첨부 작업을 복원한다.
- 수집 실패는 해당 기관의 성공 기준점을 갱신하지 않는다. 증분 인덱스·설정·ID 판정 오류는 해당 기관만 일반 수집으로 전환한다. 손상된 인덱스 원본은 `crawl_state_recovery`에 보관한다.
- OCR 재시도는 저장된 작업 기록으로 수행한다. 성공한 자료는 다운로드 없이 재사용하고 실패·부분·유예 자료만 재시도한다. 기관별 순환 및 오래된 재시도 순으로 처리하며, 예산 소진 시 이미 확보한 텍스트를 지우지 않는다.
- 목록에서 생략되거나 탐색 범위 밖인 공고는 삭제·마감으로 추정하지 않는다. 전체 history, 기존 feed v3·21일 마감 정책과 사용자 로컬 수정·삭제·복원은 기존 경로를 유지한다.

새 어댑터는 `BaseScraper`의 공통 경로를 사용하고, 목록의 `notice_id_for(item)`와 `normalize()`가 같은 ID를 생성해야 한다. `BoardScraper`·`PortalScraper`에는 이미 연결되어 있다. 전용 페이지 수집 구현은 페이지마다 `list_page_complete()`와 `may_fetch_list_page()`를 호출한다. 지원하지 않는 ID 판정은 안전한 일반 수집으로 전환한다.

Actions state artifact에는 crawl 상태·진단·복구 파일도 포함한다. 이 파일과 OCR 캐시는 Pages 공개 allowlist에 포함되지 않는다. 로컬 A/B·matcher·회사 DB 코드는 변경하지 않는다.
